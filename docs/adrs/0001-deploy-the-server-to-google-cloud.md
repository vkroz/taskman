# ADR 0001: Deploy the server to Google Cloud

Status: accepted, Nov 12, 2026. An ADR (Architecture Decision Record) records one decision. This one builds the Google Cloud target of the [deployment](../architecture.md#deployment) of the Taskman server.

## Context

The first cloud design of the Taskman server kept every organization name out of the repository. The workflow `CI` read the project, the service accounts and the other names from GitHub repository variables. A project owner did the one-time setup by hand, from a guide and a setup kit outside the repository. Requirement R9 of the epic that moved Taskman to SQL storage asked for this. It said: "The repository holds no organization-specific project IDs, service accounts or URLs", and "Cloud SQL provisioning, IAM and secrets are prerequisites and out of scope". IAM is Identity and Access Management.

The Fabric repository, ADR 0007, deploys with a different standard. One committed configuration file names every resource of an environment. `bootstrap.sh` sets up the project once. `deploy.sh` deploys one image. A GitHub workflow deploys each push to `staging`.

The product owner decided on Nov 12, 2026: Taskman uses the same deployment standard as Fabric, so that all repositories have one standard. Each push to `staging` deploys the server to Google Cloud project `nemos-infra`, region `us-central1`.

## Decision

- **One standard.** Taskman copies the deployment of the Fabric repository, ADR 0007: the file layout, the script steps and helpers, the workflow structure and the pinned actions. It differs only where the product differs: one job and one service, a public service, and a new database on a shared instance.
- **Requirement R9 amended.** Organization-specific names live only in `deploy/gcp/<environment>.env`; [`deploy/gcp/nemos-infra.env`](../../deploy/gcp/nemos-infra.env) is the first. The scripts and the workflow read them from that file. The Taskman code, its tests and the product documents hold no project IDs, service account addresses or URLs; they name only the environment file and its workflow. This ADR and the runbook [Run the Taskman server on Google Cloud](../deploy-gcp.md) describe the one environment and name its resources, as in Fabric. Cloud SQL, IAM and secrets are now in scope: [`deploy/gcp/bootstrap.sh`](../../deploy/gcp/bootstrap.sh) sets them up. Reason: one reviewed standard for all repositories is worth more than a repository without organization names.
- **Resources.** One image runs every resource ([`taskman/Dockerfile`](../../taskman/Dockerfile)). The Artifact Registry repository `taskman` holds it. The database `taskman` and its user `taskman` are on the Cloud SQL for PostgreSQL 16 instance `nemos-pg`. The Cloud Run job `taskman-db-upgrade` runs `taskman db upgrade`. The Cloud Run service `taskman` runs `taskman serve`. The job and the service run as the new service account `taskman-server`. GitHub deploys as the service account `taskman-deployer`, which exists and is reused.
- **One-time setup in the repository.** `bootstrap.sh` turns on the APIs (application programming interfaces) and creates the image repository, the service accounts and their roles, the database, and the user and its password secret. It also creates the OAuth (Open Authorization) client secret without a value, Workload Identity Federation, and the public service with a placeholder image. A repeated run creates only what is missing and never replaces a password.
- **Public service; Taskman checks tokens.** The service has no Cloud Run IAM invoker check. Taskman checks the bearer token of each call under `/api/v1/`; `/healthz` and `/readyz` need no token. Agent machines have no Google identity, so they cannot pass an IAM check. This is the one access difference from Fabric, whose services are private. `bootstrap.sh` turns off the invoker check once. `deploy.sh` passes no IAM flag, so a deployment keeps that setting. The first deployment, on Nov 14, 2026, showed that Cloud Run Developer is enough to deploy the service with this setting.
- **New database on the shared instance.** The instance `nemos-pg` in `nemos-infra` exists and serves other applications. Taskman gets its own database and user. Cloud SQL gives the user the role `cloudsqlsuperuser` on the instance. When the database or the user exists but the password secret has no value, the names belong to another application: `bootstrap.sh` stops before it sets up any resource. On each run, it sets the password of the user from the secret, so the two always match.
- **Passwords.** Cloud Run sets `TASKMAN_DB_PASSWORD`, and with browser login `TASKMAN_GOOGLE_CLIENT_SECRET`, as environment variables from Secret Manager, as Fabric does. The service account `taskman-server` reads only these two secrets.
- **Schema before the service.** [`deploy/gcp/deploy.sh`](../../deploy/gcp/deploy.sh) updates the job `taskman-db-upgrade` with the new image and runs it. A failure stops the deployment before the service changes. Then the script deploys the service. The server listens only after it connects to the database and finds the current schema, so `gcloud run deploy` fails when the new revision cannot start. A liveness probe on `/readyz` replaces an instance that lost its one database connection.
- **Deployment.** The GitHub workflow [`deploy-nemos-infra.yml`](../../.github/workflows/deploy-nemos-infra.yml) runs on each push to `staging`, which includes each merged pull request. It runs the checks of [`ci.yml`](../../.github/workflows/ci.yml), builds and pushes the image, and runs `deploy.sh` with the image digest. Thus the job and the service run exactly the image that the run built. One deployment runs at a time, and a running deployment is never cancelled. GitHub signs in through Workload Identity Federation, with the new provider `taskman` in the existing pool `github`. The provider accepts only the repository `vkroz/taskman` and the branch `staging`. The deployer binding names the pool, so it also trusts the other providers of the pool that map `attribute.repository`; `bootstrap.sh` lists them for the owner to check. There is no service account key.
- **Browser login.** A project owner creates the OAuth client in Google Auth Platform, in the Google Cloud console. The client secret goes into Secret Manager. The client ID and the allowed domains and email addresses are in the environment file. To turn browser login on, or to change who may sign in, a person commits a change of that file to `staging`.
- **Earlier resources stay.** The services `taskman-staging` and `taskman-prod`, the databases `taskman_staging` and `taskman_prod`, their secrets, and the Workload Identity Federation provider `github-actions` stay as they are. The new deployment does not use or change them.

## Options

| Option | Fit |
| --- | --- |
| GitHub repository variables and a setup kit outside the repository (the earlier design) | Keeps organization names out of the repository. But nobody reviews the setup with the code, and each repository has its own standard. |
| Secrets as mounted files | Taskman reads both files and environment variables. Environment variables match Fabric and need no volume. Docker Compose still uses a secret file. |
| Private service, with IAP (Identity-Aware Proxy) or `gcloud run services proxy` | Each call needs a Google identity. Agent machines have none. |
| Smoke test after the deploy | `gcloud run deploy` already fails when the new revision does not start, and the server starts only with a database connection and the current schema. A test after the deploy repeats this check. |

## Consequences

- A merge to `staging` reaches `nemos-infra` in one workflow run. A failed check or build changes nothing in Google Cloud. A failed schema upgrade stops the deployment before the service changes; only the job has the new image. A failure after the schema job can leave the job on the new image and the service on the previous image, until the next deployment.
- The schema upgrade runs before the new code serves. Until the service update completes, the running instances of the previous release use the new schema, and a new instance of the previous release does not start. Migrations must stay compatible with the previous release. Schema upgrades go forward only.
- Each deployment sets the environment variables and the secrets of the job and the service from the environment file. It replaces changes that a person makes by hand in the console.
- The user `taskman` can create roles and databases on the shared instance `nemos-pg`, next to those of other applications.
- GitHub shows the "Run workflow" button only when the workflow file is on the default branch. The default branch `main` has no deployment files. Thus a deployment runs again only after a new push to `staging`, or with "Re-run all jobs" of an earlier run.
- The first deployment needs the setup of the runbook, [Set up the environment once](../deploy-gcp.md#set-up-the-environment-once): `bootstrap.sh` and the GitHub environment `nemos-infra`. Another project needs its own environment file and workflow.

Open points: backup retention and recovery targets of the shared instance, a rate limit for the login pages, audit, and a production environment.
