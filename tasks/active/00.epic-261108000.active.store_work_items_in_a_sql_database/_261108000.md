## Problem

Taskman stores work items as text files under `tasks/` in each repository. Agents on different machines or checkouts cannot share one record without sharing the files. A file tree cannot serve as a hosted service.

## Objective

Taskman stores work items in a SQL database. It runs locally against SQLite or Postgres, or as a hosted server on Google Cloud Platform (GCP) Cloud Run against Cloud SQL for PostgreSQL. The lifecycle contract in `docs/specification.md` stays the same on every backend.

## Decisions (Nov 8, 2026)

- D1: The file backend stays during this epic and is retired in a later epic.
- D2: On GCP, Taskman runs as an HTTP server on Cloud Run. The CLI reaches it through a remote backend with a token. Agent machines need no GCP credentials.
- D3: Each work item belongs to a project. A repository selects its project in configuration. One database or server serves many projects.
- D4: No import from `tasks/` files. SQL backends generate their own IDs.

## Requirements

- R1 Contract preservation: every current CLI command, UI operation and lifecycle rule behaves the same on every backend. This includes drafts, finalize, journal kinds, close gates, immutability, revision invalidation, ordering, consolidation and discard.
- R2 Backend selection: `file`, `sqlite`, `postgres` or `remote`. The default stays `file` until retirement.
- R3 Projects: list, ready, browse, context and the UI show only the selected project's items. Dependencies and parents stay inside one project.
- R4 IDs: commands treat IDs as opaque. The file backend keeps `YYMMDDnnn`. SQL backends generate IDs.
- R5 Schema versions: the SQL schema has a recorded version. One command upgrades a database to the current version and does nothing when it is current. It must not reuse the name of the existing file-format `migrate` command.
- R6 SQLite: needs no external service. Several agents on one machine can write at the same time without lost updates.
- R7 Postgres: connects with a connection string, or to Cloud SQL through its unix socket.
- R8 Server: an HTTP API covers every operation the CLI and UI use, protected by a token. The workspace UI works against the server.
- R9 GCP: one container image runs on Cloud Run with settings from the environment only. Cloud SQL provisioning, IAM and secrets are prerequisites and out of scope. The repository holds no organization-specific project IDs, service accounts or URLs.
- R10 Documentation: specification, architecture and README change in the same pull request as the behavior they describe. No "previous edition" disclaimers.

## Acceptance criteria

- One contract test suite passes against the file, SQLite, Postgres and remote backends.
- All tests that exist on `main` (e21a23f) pass unchanged, except tests that hard-code the file layout. Those move to the file backend's own tests.
- Two CLI instances with different working directories share one project through a local server, and each sees the other's journal entries.
- The container image runs locally against Postgres through a unix socket with Cloud Run style environment variables.
- Plugin skills and rules need no wording change for SQL backends, or change in the same pull request.

## Risks and mitigations

- Rewrite instead of evolution: the first feature changes no behavior. Each feature lands as its own pull request.
- Token sent to a host chosen by a repository: repository configuration selects backend and project only. Tokens live in user configuration, bound to a server URL.
- Concurrency: the file backend uses a file lock. SQL backends use transactions. The contract suite includes concurrent writers.
- ID format assumptions ("9 digits" in help text and validation) break SQL IDs: R4 requires a review of every ID check.
