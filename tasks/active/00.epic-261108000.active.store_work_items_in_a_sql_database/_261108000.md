## Problem

Taskman stores work items as text files under `tasks/` in each repository. Agents on different machines or checkouts cannot share one record without sharing the files. A file tree cannot serve as a hosted service, and its Markdown structure limits the work-item model.

## Objective

Taskman stores work items in a SQL database with a work-item model like Jira or Linear. It runs locally against SQLite or Postgres, or as a hosted server on Google Cloud Platform (GCP) Cloud Run against Cloud SQL for PostgreSQL. The lifecycle rules in `docs/specification.md` (drafts, close gates, immutability, revision invalidation) stay.

## Decisions

Nov 8, 2026:
- D2: On GCP, Taskman runs as an HTTP server on Cloud Run. The CLI reaches it through a remote backend with a token. Agent machines need no GCP credentials.
- D3: Each work item belongs to a project. One database or server serves many projects. (Nov 9, 2026: work is centered on items; the item key identifies its project.)
- D4: No import from `tasks/` files. SQL storage starts clean and generates its own keys. (Confirmed on Nov 9, 2026, after the file backend retirement moved into this epic.)

Nov 9, 2026:
- D1 (revised): the file backend is retired in this epic. SQL is the only backend afterwards.
- D5: work-item model like Jira or Linear: projects with short keys; work items with keys such as TM-42 (type, title, description, status, parent, rank); typed comments replacing the journal (decision, progress, handoff, summary, verification with result); dependency links; activity history of field changes; assignees (a person or an agent name); labels.
- D6: configuration comes from environment variables, also read from a `.env` file. The same settings work for a local CLI, Docker Compose and Cloud Run.
- D7: without an explicit path, SQLite uses one shared user file, `~/.local/share/taskman/taskman.db`.
- D8: consolidation is not carried over. An agent writes summaries into the repository when it closes work.

## Requirements

- R1 Lifecycle preservation: drafts and finalize, typed comments with verification results, close gates (current summary, current passing verification, finished dependencies and descendants), immutability of closed items, revision invalidation, cycle rejection, task-is-leaf, discard of unreferenced draft leaves, and sibling ranking work on every SQL backend.
- R2 Backend selection: `sqlite`, `postgres` or `remote`. `file` remains selectable only until the retirement feature lands.
- R3 Projects: an item key such as TM-42 identifies the item and its project; no repository setting selects a project. Listings and the UI show all projects and filter by project on request. Dependencies and parents stay inside one project.
- R4 IDs: work items have keys such as TM-42. No command, help text or UI check assumes the 9-digit file IDs.
- R5 Schema versions: the SQL schema has a recorded version. One command upgrades a database to the current version and does nothing when it is current.
- R6 SQLite: needs no external service. Several agents on one machine can write at the same time without lost updates.
- R7 Postgres: connects with a connection string, or to Cloud SQL through its unix socket. The password comes from an environment variable or a mounted secret file.
- R8 Server: an HTTP API covers every operation the CLI and UI use, protected by a token. The workspace UI works against the server.
- R9 GCP: one container image runs on Cloud Run with settings from the environment only. Cloud SQL provisioning, IAM and secrets are prerequisites and out of scope. The repository holds no organization-specific project IDs, service accounts or URLs.
- R10 Documentation: specification, architecture and README change in the same pull request as the behavior they describe. No "previous edition" disclaimers.
- R11 Model features: comments, activity history, assignees and labels are available in the CLI and the UI.

## Acceptance criteria

- One contract test suite passes against the SQLite, Postgres and remote backends.
- Two CLI instances with different working directories share one project through a local server, and each sees the other's comments.
- The container image runs locally against Postgres through a unix socket with Cloud Run style environment variables.
- Plugin skills and rules describe the SQL model (comments instead of journal entries, keys instead of file IDs) in the same pull request that changes the behavior.
- No file-backend code or `tasks/` layout documentation remains after the retirement feature.

## Risks and mitigations

- Rewrite instead of evolution: feature 261108001 put every command behind one storage interface first. Each later feature lands as its own pull request, and lifecycle rules keep their tests.
- Losing lifecycle rules in the new model (the failure of the rejected feat/gcp-deploy branch): R1 lists them, and the contract suite checks each one per backend.
- Token sent to a host chosen by a repository: a committed `.env` could point the CLI at another server. Tokens and passwords come only from the user's environment or secret files; documentation warns against committing `.env`.
- Concurrency: SQL backends serialize each lifecycle operation in one transaction. The contract suite includes concurrent writers.
