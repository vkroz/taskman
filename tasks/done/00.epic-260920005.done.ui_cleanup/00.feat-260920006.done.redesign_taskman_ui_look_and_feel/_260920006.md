Redesign and rebuild Taskman's UI beyond its initial prototype. A professional, modern look and feel is the primary priority, supported by established interaction patterns for hierarchical work items.

## Reported problems

The user describes the current UI as an unfinished prototype. The right-hand task details panel appears unconditionally and cannot be hidden when it is not needed. Free-text filtering alone does not provide the required control over the work-item collection.

## Required outcomes

- Layout, typography, spacing, controls and interaction states form a coherent, professional visual design throughout the application.
- Users can navigate the work-item hierarchy while understanding parent-child relationships.
- Users can sort work items with predictable ordering that preserves an understandable hierarchy.
- Users can filter by every defined work-item metadata attribute, in addition to free-text search.
- Users can collapse and expand hierarchical content to control what is visible.
- Users can dismiss the right-hand details panel and reopen task details when needed.

## Design scope

Review the overall visual, navigation and interaction design. Keep design specifics open for a proposal rather than requiring the user to prescribe individual widgets. Layout, sorting options and defaults, filter controls and their behavior within the hierarchy remain design decisions. Visual acceptance details will be established with the design proposal.

Consider left-hand navigation and a discoverable command area beyond task creation. Include editing open tasks and task deletion in the design proposal; define deletion eligibility and handling of references before implementation. Completed tasks remain immutable. All UI operations must also be available through the CLI.

## Filtering scenarios

- Show current work and backlog while excluding completed items.
- Show only completed work.
- Restrict completed work to a specific epic, including its nested work items.
- Combine metadata filters and epic scope with the existing keyword search.

The user reports that keyword filtering exists, but attribute filtering does not. Completed work also clutters the screen; filtering alone does not meet the separate need to consolidate history into documentation.

## Local acceptance

Demonstrate navigation, sorting, metadata filtering, collapse/expand and opening/closing details on a representative multilevel work-item hierarchy. Verify filtering coverage against the full set of defined work-item metadata attributes and exercise each filtering scenario above. Confirm that task creation and access to existing task information remain available in the redesigned UI.

This draft is still collecting the user's requirements. Implementation has not been requested.
